# 시뮬레이션 라이다 수집 상태 확인 및 수정

대상은 2026-11-06 수집 상태 확인 요청의 세 항목이다. 현장 실측이나 카메라 미디어 서비스 변경은 포함하지 않는다.

## 주기 측정의 1초 유효시간

기존 전처리는 함수 진입 시 전달된 단조 시각으로 1초 이내 스캔을 고른 뒤, 점 배열 복사와 메시지 구성 후 UTC 생성 시각을 기록했다. 최종 생성 시각과 획득 시각의 차이를 다시 검사하지 않아 계약을 벗어나는 주기 측정이 만들어질 수 있었다.

격리 원본에서 A/B의 UTC 획득 시각은 동일했고, 각 스캔 나이는 1.010초였다. 두 센서의 단조 시각 차이는 약 0.149ms였다. A/B 쌍의 시간 차이와 스캔 자체의 나이는 다른 조건이며, 이번 원본은 쌍의 시간 차이 문제를 뒷받침하지 않는다. 해당 한 건의 과거 CPU 지연이나 시계 보정 기록까지 확보한 것은 아니다.

수정은 원래 단조 시각의 1초 검사와 A/B 100ms 쌍 선택을 유지한다. 먼저 선택한 점 배열을 준비한 뒤 생성 시각을 한 번 고정하고, 그 UTC 시각에서도 나이가 0~1초인 후보만 남겨 다시 선택한다. 유효한 다른 후보가 있으면 사용하며, 센서가 빠지면 availability, pair_state, pair_delta_ms를 함께 계산한다. 미래 UTC나 만료된 스캔은 PRESENT에 넣지 않는다. 원본 획득 시각·거리·각도·점 index는 바꾸지 않는다.

주기 메시지의 1초 보고 간격은 유지한다. 백엔드 계약을 완화하지 않으며, 과거 근거를 전달하는 EVIDENCE에는 주기 측정의 나이 제한을 적용하지 않는다. 격리된 원본은 재전송·삭제하지 않는다.

## 손실 카운터와 현재 상태

| 카운터 | 단위·증가 조건 | 초기화 |
|---|---|---|
| 드라이버 frame_loss | 구독자별 읽기 커서가 최신 2개 버퍼에서 건너뛴 프레임 수의 합. 여러 구독자의 손실이 중복될 수 있음 | 드라이버 프로세스 재시작 |
| 전처리 dropped_observations | 관측 구독자가 없을 때 발행한 관측 수, 또는 가득 찬 구독자별 큐(8개)에서 폐기한 관측 수의 합 | 관측 broker 재생성 |
| 전처리 dropped_scans | 센서별 최근 버퍼(32개) 용량 초과로 밀어낸 스캔 수 | 전처리 엔진 재생성 |
| 서비스별 local_dropped_messages | 로컬 전송 대기열(10개)에서 밀어낸 메시지, 로컬 INVALID_ARGUMENT/ALREADY_EXISTS 거부, 전처리의 스캔 처리 거부 누계 | 해당 서비스 상태 객체 재생성 |

10Hz 관측을 1Hz 주기 측정으로 선택하면서 오래된 후보를 정상 소비하는 동작은 dropped_scans에 포함되지 않는다. 각 카운터는 센서 점 수나 백엔드 미저장 수가 아니며 합산 누락률로 해석하지 않는다. 큐에서 실제로 폐기된 관측과 의도한 1Hz 선별도 구분한다.

기존 드라이버의 새 구독 커서는 0에서 시작한다. 따라서 재접속·추가 진단 구독이 생기면 구독 시작 이전에 버퍼에서 사라진 프레임까지 frame_loss에 더해진다. 장기간 실행 후 새 구독으로 누계가 크게 증가할 수 있으며, 이 증가량을 해당 시점의 실제 센서 미수집이나 백엔드 누락으로 해석할 수 없다. 현재 드라이버 카운터 계약을 변경하거나 과거 값을 초기화하지 않았으며, 상태 복구는 이 누계의 증가가 멈춘 것을 기준으로 한다.

기존 집계는 누계가 양수이면 계속 OBSERVATION_LOSS/DEGRADED를 표시했다. 수정 후에는 처음 발견한 양수 누계 또는 새로운 증가를 10초간 경고하고, 증가가 멈추면 해당 손실 경고를 해제한다. 실제 센서·구독 장애와 상태 파일 만료는 별도 기준으로 계속 표시한다. 카운터 원본은 초기화하거나 지우지 않는다.

로컬 상태에는 프로세스 instance_id, 관측 IPC에는 broker stream_instance_id를 추가하여 재시작을 구분한다. 식별자를 제공하지 않는 이전 producer도 카운터 감소를 재시작 후보로 보수적으로 처리한다. 백엔드 JSON 필드·HTTP 계약은 변경하지 않는다.

지속 저장 큐의 lost_messages는 복구되지 않은 영구 전송 손실을 뜻하므로 기존 OUTBOX_DATA_LOSS 경고를 유지한다. 이번 관측 손실의 자동 복구와 구분한다.

## B의 0거리 64개

실행 이미지 revision이 `d0e4b3f3b153c0709e8b333fb3ee425c0aec3619`인 시뮬레이터와 Pi 드라이버 원본을 대조했다.

- 현재 시뮬레이터 설정은 32,000 samples/s, 10 rotations/s로 회전당 3,200개를 생성한다.
- HQ 패킷 하나는 96개 노드를 담는다. `encode_hq_capsules()`는 34개 패킷을 0으로 초기화한 후 실제 점만 채우고, 마지막 64칸을 그대로 전송한다.
- Pi의 실제 A/B 원본은 3,264개였고, index 3200~3263의 64개는 모두 각도 0·거리 0·품질 0이었다. 드라이버는 SDK 거리 q2가 0이므로 SDK_INVALID_RANGE로 전달한다.
- A의 선택 구간은 270~360도라 패딩 각도 0이 제외되고, B는 0~90도라 포함된다. 요청서의 A 800개/B 864개와 같은 구조를 설명한다. 다른 실제 무효 반환은 별도로 존재할 수 있다.

따라서 이 64개는 해당 시뮬레이터 전송 패킷의 채움값이다. 현장 사각 구간이나 측정 높이 0의 근거로 해석하지 않는다. 엣지는 임의로 각도 0·거리 0 점을 제거하지 않으며 null 좌표를 유지한다.

시뮬레이터 담당 수정 범위는 마지막 HQ 패킷의 채움 노드가 스캔으로 집계되지 않도록 패킷 경계를 연속 스트림으로 처리하는 것이다. 실제 측정점을 늘리거나 복제하여 96의 배수로 맞추면 안 된다. 공식 SDK를 통한 회전별 점 수·순서·시작 플래그·유효한 0도 및 실제 무효 거리 보존을 검증해야 한다. 이 엣지 수정은 시뮬레이터 이미지 자체를 변경하지 않는다.

## 검증 범위

회귀 테스트는 UTC 0.999/1.000/1.001/1.010초, 미래 UTC, 점 배열 준비 중 지연, 재선택 후 한 센서만 유효한 경우, A/B 100ms 경계, 과거 EVIDENCE, 손실 경고 복구와 다른 장애 유지, 프로세스·카운터 재시작을 확인한다. 운영 반영 결과는 검증한 커밋·컨테이너 이미지와 관찰 기간을 함께 회신한다.

### 적용 및 검증 결과

- 실행 코드: `b0440086235ae5c7d5a03624b8e990a01a282db8`. 로컬 Python 테스트 219개와 린트, PR의 platform-ci·camera-ci·ARM64 이미지 5종 빌드 통과.
- Pi ARM64의 별도 읽기 전용 테스트 컨테이너에서도 전체 219개 테스트 통과.
- 사용자 승인 후 전처리·전송·오케스트레이터 3개만 수정 이미지로 교체했다. 드라이버·카메라 컨테이너와 시뮬레이터는 교체하지 않았다. 설정·비밀·기존 저장 큐의 경로를 유지하고 이전 이미지 ID와 Compose를 별도로 확보했다.
- 교체 후 45.1초간 실제 주기 메시지 45건을 관찰했다. 90개 센서 스캔의 최대 생성 시점 나이는 0.143초였고 모두 MATCHED였다. 관찰 중 백엔드 저장 ACK 30건을 확인했다. 이는 전체 ACK 총량이 아닌 관찰자가 확인한 부분 집계다.
- 새 격리 건은 없었고 기존 격리 1건을 그대로 보존했다. 원본 파일의 SHA256은 변경 전과 같았다. 전송 lost_messages는 0이었다.
- 이후 상태 확인에서 드라이버 A/B·전처리·전송·카메라·오케스트레이터 모두 HEALTHY, 손실 사유 없음으로 확인했다. 이 결과는 짧은 연동 관찰 결과이며 장기간 무결함 보장은 아니다.
- B의 패딩 64개는 시뮬레이터 이미지의 별도 수정 대상이다. 이 배포에서 제거하거나 높이 0으로 대체하지 않았다.
