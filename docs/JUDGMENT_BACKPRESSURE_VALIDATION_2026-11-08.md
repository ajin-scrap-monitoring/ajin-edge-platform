# 판단 묶음 폐기 경로 수정과 Pi 재시험

구현 소스는 `87cefc71208f9e1fee4598168041b25e88e8f8c3`이다.
기존 수집·설정 API 검증에 이어 판단 묶음의 대기열 덮어쓰기 경로를 수정했다.

## 확인한 원인과 역사적 사건의 한계

기존 PendingSender.offer는 대기 슬롯1개가 차면 그 안의 이전 묶음을 폐기하고 새 묶음을 넣었다.
이미 처리 중인 묶음 외에 다음 묶음이 기다리는 동안 저장 작업이 느려지면,
1초마다 계속 생성되는 새 판단이 이전 판단과 원본 근거 묶음을 덮어썼다.
5스캔×A/B와 판단1개가 묶이면 폐기 카운터는 한 번에11 증가한다.

Pi의 실제 SDK 입력을 유지한 격리 환경에서 원본 코드의 저장 stage에3초 지연을 한 번 주입했다.
계측 결과 LOCAL_DELIVERY_BACKLOG_LOSS와 함께11메시지 묶음이 두 번 교체되어 총22개 폐기가 발생했다.
해당 재현에서 INVALID_ARGUMENT/ALREADY_EXISTS 영구 거부는 원인이 아니었다.

이전에 관측한 단일11건 사건은 당시 상세 계측이 없어 그 발생 시각과 지연 유발 요인을 소급 확정할 수 없다.
이번에 동일 형태의 폐기를 일으키는 코드 경로를 직접 재현하고 수정한 사실과 구분한다.

## 수정

오케스트레이터의 단일 판단 생성자는 대기 슬롯이 생길 때까지 비동기로 기다린 뒤,
그 시점의 최신 관측으로 다음 판단을 계산한다. 공간을 기다리기 전에 완성된 추가 묶음을 만들지 않는다.
슬롯이 풀리면 Event로 깨우며, 생성 주기의 기준도 대기 완료 뒤에 잡는다.

- 대기1개+처리 중1개와 최근 관측 이력, 입력 만료·A/B 정합,4GiB 임시 저장 한도 유지.
- 관측 소비·전처리 정기 전송·원본 점·판단 수식·설정 ACK 경로 유지.
- 잘못된 메시지에 대한 영구 거부 처리를 없애거나 무한 재시도로 숨기지 않음.
- 느린 소비자에서 계산 전 대기, 전체 순서 전달, 대기 취소 후 기존 묶음 보존 회귀 추가.

로컬 및 Pi ARM64 읽기 전용 격리 Docker 회귀는 각각356개가 통과했다.
린트·sdist/wheel, 독립 검토, 플랫폼·카메라 CI, SDK AddressSanitizer와 ARM64 이미지5종 빌드도 통과했다.

## 같은 저장 지연의 수정 전후 비교

운영과 같은 SDK 드라이버 UDS를 사용하지만 별도 설정·상태·큐·제어 폴더 및 ACK 시험 수신기를 사용했다.
운영 백엔드 DB 성능 시험으로 표현하지 않는다.

| 같은3초 stage 지연 | 기존6256f7e | 수정87cefc7 |
|---|---:|---:|
| 폐기된 판단 묶음 | 2 | 0 |
| 폐기된 메시지 증가 | 22 | 0 |
| 수정본의 생성 측 공간 대기 | 해당 없음 | 약1.970초 |

수정본에서는 fault 전후 관측 폐기 누계18이 증가하지 않았고, 정기 전송·저장 손실도 증가하지 않았다.
이18은 준비·설정 구독 구간의 기존 누계이며 시험 전체가 누락0이었다고 표현하지 않는다.
이후 새 설정 세대의 별도 준비 구간을 거쳐 아래600초 구간을 계측했다.

데이터 생성자는 별도 worker에서 관측을 계속 받았고, 개발 테스트나 빌드는 측정 중 실행하지 않았다.

## 운영 적용 및 범위

검증 이미지로 데이터 서비스3개와 설정 API를 교체하고 기존 설정·큐·인증을 보존했다.
네 컨테이너 healthy와 운영45초 구간의 추가 관측·판단·저장 손실0을 확인했다.
실제 백엔드의 최근45초 측정44건은 생성 간격 중앙값1.001초, p99/최대1.024초였으며,
최신 A/B 스캔의1,600점에 XYZ가 포함된 것을 확인했다. 이는 전체 판단 모델을 활성화한 운영 시험은 아니다.
기존 격리1건은 보존했고 현재 전송 대기는 측정 종료 시1건이었다.
운영 설치 보정과 원본 XYZ 전달은 유지하며 전체 판단 모델은 실제 백엔드의 확장 계약 수용 전 활성화하지 않는다.
`position_mm.z`는 반사점 world Z이며 현재 바닥 Z=0에서만 바닥 상대 높이와 수치상 같다.
필터·중앙값·보간 뒤 bin별 바닥을 뺀 판단 `height_mm`과 구분한다.

설정 변경·재시작에서 생기는 짧은 입력 공백과 기존 운영·시험의 과거 누계는 별도로 보존한다.
이전 누계를 지워 전체 운영 이력의 손실0으로 바꾸지 않는다.
