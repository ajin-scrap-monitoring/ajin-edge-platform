# Pi 처리 주기 및 보정 수신 API 구현 계획

> 실행: 기존 별도 worktree에서 단계별 실패 회귀 검사→수정→검증. 원인 계측과 완료 전 검증을 적용한다.

## 목표와 제약

- 실제 SDK 입력에서 전처리 관측·1초 판단·근거 저장 전송이 서로 밀리지 않게 한다.
- 원본 점·근거 보존, 최대 100ms 시간 정합, 1초 입력 만료와 4GiB 저장 예산을 유지한다.
- 설치 보정 API를 통해 인증된 보정값을 받고 새 설정 저장 ACK 후 좌표 계산에 적용한다.
- 운영 주소·토큰·실제 점 배열을 공개하지 않는다. 백엔드 구현은 변경하지 않는다.

## 원인 근거

Pi 실시간 입력 65초 계측에서 전처리 ingest 중앙값 약35ms, 이벤트 루프 지연 중앙값166ms였다.
단면 판단은 중앙값238ms였지만 근거 Enqueue RPC 중앙값109ms, 로컬 enqueue40ms·ACK43ms로
큰 본문의 반복 저장이 이어졌다. 큐 크기나 시간 창을 늘려 해결한 것으로 간주하지 않는다.

## 설계

### 계산·전송

전처리의 ingest와 periodic 상태 접근을 단일 계산 worker에 직렬화한다. gRPC/관측 이벤트 루프와 분리하고
큐는 센서당 진행 중 입력 하나와 주기 작업으로 유한하게 유지한다. worker 내부에서 판정 시각을 취한다.

ACK는 이미 사용 중인 내구성 receipt 메타데이터로 우선 기록하고 보호된 대용량 본문을 매번 다시 쓰지 않는다.
재시작 시 receipt를 반영해 전송 완료 상태를 복구한다. 최근 receipt32개를 넘겨 잊기 전에 아직 남아 있는
보호 레코드의 ACK 상태를 본문에 확정하여 중복 재전송·근거 소실을 막는다. 원자 쓰기·fsync·참조 보호는 유지한다.
상태 저장과 기타 실제로 확인한 지연은 계측 결과에 따라 처리한다.
실측에서 남은 단일 요청·개별 ACK 동기화 병목은 HTTP 최대4건 병렬 전송과 ACK 묶음의 단일 메타데이터
동기화로 처리한다. 각 요청 본문·ID·저장 ACK는 독립이며 실패한 본문은 그대로 재시도한다.
전송 중 ID를 중복 선택하지 않고 ACK 확정 전 참조·전송 보호를 해제하지 않는다.
ACK 뒤 파일 삭제의 디렉터리 동기화도 한 작업 안에서 묶되 작업 반환 전에 확정한다.
실제 입력의 잔여 대기 폐기로 확인한 근거 저장 경로는 최대4개·16MiB의 내부 stage RPC로 묶는다.
각 원본 파일의 fsync는 유지하고 마지막 디렉터리 동기화를 묶어 RPC 성공 전에 확정한다.
영속 begin lease와 commit의 근거 정합 검증은 유지하며 부분 stage 실패는 동일 본문으로 재시도한다.
ACK receipt 순환은 보존된 원본 파일의 ACK 표식 rename과 디렉터리 fsync로 확정한다.
따라서 보호 저장소가 가득 차도 원본의 두 번째 복사 공간을 요구하지 않는다.

### 보정 수신 API

Pi 제어용 HTTP JSON 서비스 `edge-v2 calibration-api`를 추가한다. aiohttp를 사용한다.
기본은 loopback이고 명시한 Tailscale 인터페이스만 외부 바인딩한다. 전용 Bearer 토큰 파일을 사용하며
기존 백엔드 전송 토큰을 공유하지 않는다. 요청 본문은32KiB, 제어 상태는128KiB 이내로 제한한다.

- `PUT /api/control/v1/calibrations`: Idempotency-Key와 site_id, edge_id, base_config_revision,
  config_revision, coordinate_frame_id, calibrations[{sensor_id, calibration}]를 받는다.
- calibration은 기존 version, verification_state, angle_sign, angle_zero_offset_mdeg, rotation,
  translation_mm 형식을 재사용한다. mm와 오른손 직교 회전 행렬, 유한 수, 센서 허용 목록을 검증한다.
- 한 번에 A/B 중 하나 또는 둘을 갱신한다. 같은 버전의 다른 값·기준 revision 충돌·다른 좌표계는 거부한다.
- 수신만으로 VERIFIED로 바꾸지 않는다. 미검증 값이면 좌표는 기존 규칙대로 null이다.
- `GET /api/control/v1/calibrations`와 `GET /api/control/v1/calibration-jobs/{id}`는 인증 후
  현재 보정·진행 상태를 제공한다. 토큰·백엔드 주소·파일 경로를 반환하지 않는다.

제어기는 새 등록 메시지를 기존 uplink에 넣고 백엔드 저장 ACK를 기다린다. ACK 전에는 활성 설정을
바꾸지 않는다. 거부 시 기존 설정을 유지하고 실패를 알린다. 수신은202, 적용 완료 여부는 조회로 확인한다.
보정 상태 파일은 전용 control_dir 안의 단일 파일로 원자 저장한다. API만 쓰기 가능하게 mount하고
계산·전송 서비스에는 디렉터리를 읽기 전용으로 제공한다. status_dir과 분리하여 상태 기록 권한으로
보정값을 변경할 수 없게 한다. 상태와 보정 폴더의 실제 사용량은 기존1MiB 보조 예산과 전체4GiB에 합산한다.
과거 요청 응답64개와 버전 충돌 기록을 유한하게 유지하고 상한 초과 시 거부한다.
동시에 하나의 pending 요청만 허용하고 요청 해시·기준 revision·완전한 등록 본문·고정 message_id를
202 응답 전에 영속 저장한다. 단일 writer 잠금과 적용 직전 기준 revision 재확인을 사용한다.
재시작 후 ACK 증명이 최근32개 receipt에서 사라졌으면 동일 등록 메시지를 재전송하여 중복 ACK를
확인한다. 레코드가 없다는 이유로 ACK를 추정하지 않는다. quarantine은 최종 거부 상태다.
활성 설정·ACK·적용 경계를 한 번의 원자 상태 교체로 확정하고 각 서비스의 새 revision 보고 전에는
APPLIED로 응답하지 않는다. 초기 및 이후 버전 해시를 영속 유지한다.

서비스는 이 활성 설정 파일의 변경을 감시한다. 활성 revision 변경 시 해당 서비스 루프를 정상 정지·정리하고
새 설정으로 시작하여 기존 이력·보간값을 섞지 않는다. 영속 전송 큐는 유지한다.
드라이버 획득 설정 revision은 별도로 고정 검증하고 보정 계산 revision과 구분한다.
스키마·센서·edge 식별 검증은 완화하지 않는다. 적용 이전 획득 스캔은 새 보정 계산에 사용하지 않는다.
재시작·신규 boot에서 단조 시각 적용 경계를 잘못 재사용하지 않는다.
획득 revision은 배포 기준에서 명시적으로 고정하고 API가 바꾸지 못하게 한다. 제어 파일의 기준 식별자가
배포 기준과 다르거나 파일이 소실·손상되면 이전 보정으로 조용히 되돌아가지 않고 적용을 중단한다.

새 판단 모델이 없는 운영 설정에는 보정만 갱신할 수 있다. 새 단면·종합 필드의 백엔드 미지원 문제를
보정 API로 우회하지 않는다. 시험 보정·가중치를 운영 검증값으로 자동 입력하지 않는다.

## 완료 기준

정상 입력과 정상 시험 ACK 하에 초기 준비 이후 최소10분 동안 관측 누락과 대기 묶음 폐기가 증가하지 않는다.
판단 생성·전달 주기를 각각 측정하고 p99 간격1.2초 이내, 최대1.5초 이내를 목표로 하며 결과를 수치로 기록한다.
이는 하드 실시간 보장이 아니다. 입력 불량·시간 불일치·실제 장애는 수치를 꾸미지 않고 이유를 보고한다.
네트워크 장애 때에도 유한 큐·저장 상한·손실 보고를 유지하며 무손실을 약속하지 않는다.
보정 적용 시험은 운영과 분리한 실제 입력 경로에서 수행하고, 운영 입력값은 검증된 요청으로만 활성화한다.
