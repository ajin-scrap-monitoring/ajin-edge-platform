# 실제 전송 적체 원인 계측·수정 계획

목표: Pi와 백엔드의 실제 처리시간을 분리하고 적체 증가 원인을 수정한 뒤,
실제 입력에서 대기가 지속 증가하지 않으면 기본 판단을 다시 활성화한다.

기존 worktree의 fix/uplink-backlog-throughput에서 직접 구현하며 main의 사용자 파일은 유지한다.
원본·EVIDENCE·판단 수식·1초 기본 주기·4GiB 상한·저장 ACK·재시도 조건을 유지한다.

## 현재 근거

- 실제 적체 약6천 파일의 전체 물리 사용량 스캔 중앙값55.7ms.
- 79.9초 전달 step 구간에서 반복 스캔530회·30.1초, fsync 총4.94초.
- 실제 HTTP ACK 중앙값 EVIDENCE178.5ms, PERIODIC225.2ms, assessment143.3ms.
- 설정 메시지는 일반 최신/최구 전송 선택에 섞여 대량 적체 중 제어 ACK가 지연된다.
- 이는 Pi의 불필요한 반복 작업을 확인한 근거이며 백엔드 처리량 전체가 충분하다는 증거는 아니다.

## 수정 경계

단일 writer 잠금 아래 파일별 실제 할당량을 유지하고, 시작 시와 상태 감사 때 전체 디렉터리를 재검사한다.
write·replace·rename·delete·부분 실패마다 실제 할당량을 갱신하며 실패 시 재감사한다.
임시 파일을 포함한 실제 물리 예산과 외부 status/control 예산·실제 여유 디스크 검사·fsync는 유지한다.
설정은 pending 중 우선 선택하고 일반 데이터의 최신/최구 순환은 유지한다.
서버 수신 비용이 추가로 병목이면 같은 실제 데이터로 HTTP·서버 단계 비용을 더 분해해 수정한다.

## 검토 초점

할당량 캐시가 부분 실패·ACK rename·재시작 후 공간을 누락하는 경우,
임시 파일이 예산에서 빠지는 경우, 외부 status 사용량을 오래된 값으로 판단하는 경우,

## 추가 확인과 수정

Pi 개선만으로는 판단 활성 시 적체가 남았다. 백엔드에서 EVIDENCE까지 사용하지 않는
live projection 행 잠금을 취하는 문제를 확인해 별도 수신 수정으로 분리했다.
원본 artifact unique 제약·savepoint·저장 후 ACK는 유지한다.

두 개선 후 첫600초 관측의 분별 대기 중앙값은8/15/8/8/19/4/4/1/8/16건이었다.
그러나 최종62건, 전체 기울기0.01235건/초로 사전 기준0.01을 넘어서 판단을 다시 중단했다.
이 구간은 통과로 표현하지 않는다.

전송기는4개 요청 중 가장 늦은 하나를 기다리며 완료된 슬롯도 재사용하지 않고 있었다.
지연 요청 하나를 잡아 둔 회귀에서 다섯 번째 요청이 출발하지 못하는 것을 재현했다.
동시 HTTP·pin 상한4개는 유지하고 완료·내구 ACK·unpin 후 빈 슬롯을 재사용한다.
한 turn은 최대16건, 새 선택의 시간 예산은1초로 제한해 상태·토큰 확인과 종료 기회를 보장한다.
이미 시작한 디스크 선택이나 HTTP 응답을1초에 강제 취소한다는 의미는 아니다.
재시도·인증·설정 오류를 발견하면 새 출발을 중지하고 이미 진행 중인 요청만 정리한다.
취소 중 executor의 늦은 pin도 회수하며 ACK를 못 받은 본문은 pending으로 유지한다.
이 수정의 회귀370개·독립 검토·CI·ARM64 Docker370개가 통과했다.
백엔드도 일반1,755개·PostgreSQL1,415개 및 별도 동시 저장 검증을 통과했다.
일반 실행 entrypoint의 운영 입력 재시험과 추가 연속 관측에서 사전 적체·추가 손실 기준을 통과해
기본 판단의 활성 상태를 유지했다. 실제 표본·상세 측정 기록·배포 공백 이력은 로컬 회신에 분리해 보존했다.
적체 안정은 모든 HTTP 수신 간격이1초 이하라는 보장이나 현장 정확도 검증을 의미하지 않는다.
